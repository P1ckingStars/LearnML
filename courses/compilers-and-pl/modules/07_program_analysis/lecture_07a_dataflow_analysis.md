# Lecture 07a: Dataflow Analysis

## 1. Introduction

Dataflow analysis is a family of techniques for computing information about the flow of data through a program. These analyses determine facts that hold at each program point---which definitions reach a point, which variables are live, which expressions have already been computed---enabling transformations that improve performance without changing behavior.

The power of dataflow analysis lies in its mathematical foundation: lattice theory, monotone functions, and fixed-point theorems provide a uniform framework for defining, computing, and reasoning about correctness of diverse analyses.

---

## 2. The Dataflow Analysis Framework

### 2.1 Control Flow Graphs

A dataflow analysis operates on a control flow graph (CFG) $G = (N, E, \text{entry}, \text{exit})$ where $N$ is the set of nodes (basic blocks or individual instructions), $E \subseteq N \times N$ is the set of control flow edges, and $\text{entry}, \text{exit}$ are distinguished entry and exit nodes.

### 2.2 Lattices

**Definition (Partial Order).** A *partial order* $(L, \sqsubseteq)$ is a set $L$ with a binary relation $\sqsubseteq$ that is:
- Reflexive: $\forall x.\; x \sqsubseteq x$
- Antisymmetric: $x \sqsubseteq y \land y \sqsubseteq x \implies x = y$
- Transitive: $x \sqsubseteq y \land y \sqsubseteq z \implies x \sqsubseteq z$

**Definition (Complete Lattice).** A *complete lattice* $(L, \sqsubseteq, \sqcap, \sqcup, \top, \bot)$ is a partial order where every subset $S \subseteq L$ has:
- A greatest lower bound (meet): $\bigsqcap S$
- A least upper bound (join): $\bigsqcup S$
- Top element: $\top = \bigsqcap \emptyset$
- Bottom element: $\bot = \bigsqcup \emptyset$

**Example.** For a set of definitions $D$, the powerset lattice $(\mathcal{P}(D), \subseteq, \cap, \cup, D, \emptyset)$ is a complete lattice.

### 2.3 Transfer Functions

Each node $n$ in the CFG has a *transfer function* $f_n : L \to L$ that describes how the node transforms the dataflow information.

For many analyses, transfer functions have the form:

$$f_n(x) = \text{Gen}_n \cup (x \setminus \text{Kill}_n)$$

where $\text{Gen}_n$ is the set of facts generated by $n$ and $\text{Kill}_n$ is the set of facts killed by $n$.

### 2.4 Meet/Join Operators

At confluence points (where multiple paths merge), dataflow information is combined using the meet ($\sqcap$) or join ($\sqcup$) operator, depending on the analysis direction and whether we seek may or must information.

- **May analysis** (e.g., reaching definitions): use $\cup$ (join). A fact holds if it holds on *any* path.
- **Must analysis** (e.g., available expressions): use $\cap$ (meet). A fact holds only if it holds on *all* paths.

### 2.5 The General Framework

A *monotone dataflow framework* is a tuple $(L, \sqsubseteq, F, \text{direction})$ where:
- $(L, \sqsubseteq)$ is a complete lattice with finite height.
- $F$ is a set of monotone transfer functions $f : L \to L$.
- Direction is forward or backward.

**Forward analysis:**

$$\text{In}[n] = \bigsqcap_{p \in \text{pred}(n)} \text{Out}[p]$$

$$\text{Out}[n] = f_n(\text{In}[n])$$

**Backward analysis:**

$$\text{Out}[n] = \bigsqcap_{s \in \text{succ}(n)} \text{In}[s]$$

$$\text{In}[n] = f_n(\text{Out}[n])$$

## 3. Forward Analyses

### 3.1 Reaching Definitions

**Problem.** For each program point $p$, determine which definitions $d : x := \ldots$ *may reach* $p$ without being killed by an intervening redefinition of $x$.

**Lattice:** $(\mathcal{P}(D), \subseteq)$ where $D$ is the set of all definitions in the program. Meet is $\cup$ (union---may analysis).

**Transfer function:**

$$f_n(x) = \text{Gen}[n] \cup (x \setminus \text{Kill}[n])$$

- $\text{Gen}[n] = \{d\}$ if $n$ is definition $d$.
- $\text{Kill}[n] = \{d' \in D : d' \text{ defines the same variable as } n\} \setminus \text{Gen}[n]$.

**Dataflow equations (forward):**

$$\text{In}[n] = \bigcup_{p \in \text{pred}(n)} \text{Out}[p]$$

$$\text{Out}[n] = \text{Gen}[n] \cup (\text{In}[n] \setminus \text{Kill}[n])$$

**Initialization:** $\text{Out}[\text{entry}] = \emptyset$ (or $\{d_0^x : x \text{ is a parameter}\}$), $\text{Out}[n] = \emptyset$ for all other $n$.

### 3.2 Available Expressions

**Problem.** For each program point $p$, determine which expressions have been *definitely computed* on every path from the entry to $p$, and not subsequently invalidated.

**Lattice:** $(\mathcal{P}(E), \supseteq)$ where $E$ is the set of all expressions. Note the reversed order: $\top = E$ (all expressions), $\bot = \emptyset$. Meet is $\cap$ (intersection---must analysis).

**Transfer function:**

$$f_n(x) = \text{EGen}[n] \cup (x \setminus \text{EKill}[n])$$

- $\text{EGen}[n]$: expressions computed at $n$ whose operands are not subsequently redefined at $n$.
- $\text{EKill}[n]$: expressions containing variables defined at $n$.

**Dataflow equations (forward):**

$$\text{In}[n] = \bigcap_{p \in \text{pred}(n)} \text{Out}[p]$$

$$\text{Out}[n] = \text{EGen}[n] \cup (\text{In}[n] \setminus \text{EKill}[n])$$

**Initialization:** $\text{Out}[\text{entry}] = \emptyset$, $\text{Out}[n] = E$ (all expressions) for all other $n$.

**Application:** Common subexpression elimination (CSE). If expression $e$ is available at a point where $e$ is computed, the recomputation can be replaced by a reference to the previously computed value.

## 4. Backward Analyses

### 4.1 Live Variable Analysis

**Problem.** At each program point $p$, determine which variables *may be used* on some path from $p$ to the exit before being redefined.

**Lattice:** $(\mathcal{P}(V), \subseteq)$ where $V$ is the set of all variables. Meet is $\cup$ (may analysis).

**Transfer function:**

$$f_n(x) = \text{Use}[n] \cup (x \setminus \text{Def}[n])$$

- $\text{Use}[n]$: variables used at $n$ before any definition at $n$.
- $\text{Def}[n]$: variables defined at $n$.

**Dataflow equations (backward):**

$$\text{Out}[n] = \bigcup_{s \in \text{succ}(n)} \text{In}[s]$$

$$\text{In}[n] = \text{Use}[n] \cup (\text{Out}[n] \setminus \text{Def}[n])$$

**Initialization:** $\text{In}[\text{exit}] = \emptyset$ (or the set of globally live variables), $\text{In}[n] = \emptyset$ for all other $n$.

**Application:** Dead code elimination: if a definition $d : x := e$ is at a point where $x$ is not live after $d$, the definition is dead and can be removed.

### 4.2 Very Busy Expressions

**Problem.** An expression $e$ is *very busy* at point $p$ if on *every* path from $p$ to the exit, $e$ is evaluated before any of its operands are redefined.

**Lattice:** $(\mathcal{P}(E), \supseteq)$ with meet $\cap$ (must analysis, backward).

**Transfer function:**

$$f_n(x) = \text{Use}_E[n] \cup (x \setminus \text{Kill}_E[n])$$

**Dataflow equations (backward):**

$$\text{Out}[n] = \bigcap_{s \in \text{succ}(n)} \text{In}[s]$$

$$\text{In}[n] = \text{Use}_E[n] \cup (\text{Out}[n] \setminus \text{Kill}_E[n])$$

**Application:** Code hoisting: very busy expressions can be computed earlier (at the point where they become very busy), reducing code size when the expression occurs in multiple branches.

## 5. Worklist Algorithm

### 5.1 Algorithm

The worklist algorithm efficiently computes the fixed point by maintaining a set of nodes whose dataflow information may need updating.

```
Algorithm: WorklistSolver(CFG, L, transfer, direction)
Input: CFG, lattice L, transfer functions, analysis direction
Output: In[n] and Out[n] for all nodes n

1.  Initialize:
2.      For each node n:
3.          If direction = forward:
4.              Out[n] = initial value (top or bottom, depending on analysis)
5.          Else:
6.              In[n] = initial value
7.      worklist = all nodes in CFG

8.  While worklist is non-empty:
9.      Remove a node n from worklist
10.     If direction = forward:
11.         In[n] = meet over all predecessors p: Out[p]
12.         old = Out[n]
13.         Out[n] = transfer_n(In[n])
14.         If Out[n] != old:
15.             Add all successors of n to worklist
16.     Else (backward):
17.         Out[n] = meet over all successors s: In[s]
18.         old = In[n]
19.         In[n] = transfer_n(Out[n])
20.         If In[n] != old:
21.             Add all predecessors of n to worklist
```

### 5.2 Proof of Termination

**Theorem 5.1.** The worklist algorithm terminates for any monotone dataflow framework over a lattice of finite height.

*Proof.* Define the global state as the tuple $(d_1, d_2, \ldots, d_{|N|})$ where $d_i$ is the dataflow value at node $i$ (either $\text{In}[i]$ or $\text{Out}[i]$, depending on what the transfer function produces).

At each iteration, we update some $d_i$ using a monotone transfer function and a meet/join of neighboring values. We show that dataflow values can only move in one direction in the lattice:

For a forward may-analysis with join ($\cup$), values can only grow (add elements). Since the lattice has finite height (bounded by $|D|$ for bit-vector analyses), each value can change at most $h$ times, where $h$ is the lattice height. With $|N|$ nodes, the total number of changes is at most $|N| \cdot h$, which is finite.

For a forward must-analysis with meet ($\cap$), values can only shrink. The argument is symmetric.

Each worklist iteration performs at least one comparison and potentially one change. If no change occurs, the node is not re-added to the worklist. Therefore, the total number of iterations is bounded by $|N| \cdot h + |N|$ (the $+|N|$ for the final pass that detects convergence). $\square$

### 5.3 Iteration Order

The order in which nodes are removed from the worklist affects performance (not correctness):

- **Reverse postorder** (for forward analyses): processes nodes in an order such that a node is visited after most of its predecessors. Typically converges in 2--3 passes for reducible CFGs.
- **Postorder** (for backward analyses): symmetric to reverse postorder.
- **Strongly connected component (SCC) ordering**: process SCCs in topological order; iterate within each SCC. Optimal for reducible CFGs.

**Theorem 5.2.** For a reducible CFG with $d$ the maximum loop nesting depth, the worklist algorithm with reverse postorder converges in at most $d + 2$ passes.

## 6. MOP vs MFP

### 6.1 Meet Over All Paths (MOP)

The *ideal* solution at a node $n$ considers every path from the entry to $n$:

$$\text{MOP}[n] = \bigsqcap_{p \in \text{Paths}(\text{entry}, n)} f_p(\iota)$$

where $f_p = f_{n_k} \circ f_{n_{k-1}} \circ \cdots \circ f_{n_1}$ is the composition of transfer functions along path $p$, and $\iota$ is the initial value at the entry.

Computing MOP is in general undecidable (there may be infinitely many paths due to loops).

### 6.2 Maximal Fixed Point (MFP)

The MFP is the solution computed by the iterative algorithm:

$$\text{MFP}[n] = \text{In}[n] \text{ at the fixed point of the iterative equations}$$

### 6.3 Relationship

**Theorem 6.1.** For a monotone framework, $\text{MOP}[n] \sqsubseteq \text{MFP}[n]$ for all nodes $n$.

*Proof.* The MFP merges dataflow information at join points using the meet operator. For any path $p$ from entry to $n$, we can show by induction on path length that $f_p(\iota) \sqsubseteq \text{MFP}[n]$. Therefore:

$$\text{MOP}[n] = \bigsqcap_{p} f_p(\iota) \sqsubseteq \text{MFP}[n]$$

The inequality arises because MFP applies transfer functions to already-merged information, while MOP applies them to each path individually before merging. $\square$

### 6.4 Distributive Frameworks

**Definition.** A framework is *distributive* if all transfer functions distribute over meet:

$$f(x \sqcap y) = f(x) \sqcap f(y)$$

**Theorem 6.2.** For a distributive framework, $\text{MOP} = \text{MFP}$.

*Proof.* We need to show $\text{MFP}[n] \sqsubseteq \text{MOP}[n]$. Consider a node $n$ with predecessors $p_1, \ldots, p_m$. In the MFP:

$$\text{In}[n] = \bigsqcap_{i} \text{Out}[p_i] = \bigsqcap_{i} f_{p_i}(\text{In}[p_i])$$

By distributivity, applying any transfer function to the meet equals the meet of applications. By induction, this propagates back to the entry, showing that the MFP at $n$ equals the meet over all paths. $\square$

**Key consequence.** Gen/Kill transfer functions of the form $f(x) = \text{Gen} \cup (x \setminus \text{Kill})$ are distributive. Therefore, reaching definitions, liveness, available expressions, and very busy expressions all achieve the MOP solution.

## 7. Bit-Vector Frameworks

### 7.1 Definition

A *bit-vector framework* represents dataflow values as bit vectors (elements of $\{0, 1\}^n$), with meet as bitwise AND or OR, and transfer functions as:

$$f(x) = (x \mathbin{\&} \overline{\text{Kill}}) \mathbin{|} \text{Gen}$$

where $\&$ is bitwise AND, $|$ is bitwise OR, and $\overline{\text{Kill}}$ is the bitwise complement of Kill.

### 7.2 Properties

- All bit-vector frameworks are distributive.
- Operations are $O(n/w)$ per node where $n$ is the number of bits and $w$ is the machine word size (e.g., 64).
- Total complexity for a bit-vector analysis: $O(|E| \cdot n / w)$ per iteration, with $O(d)$ iterations for reducible CFGs.

### 7.3 Summary of Standard Analyses

| Analysis | Direction | Meet | Gen | Kill | Distributive |
|----------|-----------|------|-----|------|-------------|
| Reaching Definitions | Forward | $\cup$ | Defs at $n$ | Other defs of same var | Yes |
| Available Expressions | Forward | $\cap$ | Exprs computed at $n$ | Exprs with vars def'd at $n$ | Yes |
| Live Variables | Backward | $\cup$ | Vars used at $n$ | Vars def'd at $n$ | Yes |
| Very Busy Expressions | Backward | $\cap$ | Exprs used at $n$ | Exprs with vars def'd at $n$ | Yes |

## 8. The Monotone Framework Theorem

### 8.1 Statement

**Theorem 8.1 (Monotone Framework Theorem, Kam & Ullman 1977).** Let $(L, \sqsubseteq)$ be a complete lattice of finite height, and let $F$ be a set of monotone functions on $L$ (i.e., $x \sqsubseteq y \implies f(x) \sqsubseteq f(y)$ for all $f \in F$). Then the system of dataflow equations has a unique least fixed point, which is computable by iterative application of the equations starting from $\bot$.

### 8.2 Proof

*Proof.* We apply the Knaster-Tarski fixed-point theorem. Define the product lattice $L^{|N|}$ with componentwise ordering. The system of dataflow equations defines a function $\Phi : L^{|N|} \to L^{|N|}$:

$$\Phi(d_1, \ldots, d_{|N|}) = (f_1(m_1(d)), \ldots, f_{|N|}(m_{|N|}(d)))$$

where $m_i(d)$ computes the meet of dataflow values from $i$'s predecessors (or successors for backward analyses).

**Monotonicity of $\Phi$.** If $(d_1, \ldots, d_{|N|}) \sqsubseteq (d'_1, \ldots, d'_{|N|})$ componentwise, then for each $i$:
- $m_i(d) \sqsubseteq m_i(d')$ because meet is monotone in each argument.
- $f_i(m_i(d)) \sqsubseteq f_i(m_i(d'))$ because each $f_i$ is monotone.

Therefore $\Phi(d) \sqsubseteq \Phi(d')$.

**Existence of least fixed point.** By Knaster-Tarski, every monotone function on a complete lattice has a least fixed point, given by:

$$\text{lfp}(\Phi) = \bigsqcap \{d \in L^{|N|} : \Phi(d) \sqsubseteq d\}$$

**Computability.** Since $L$ has finite height $h$, $L^{|N|}$ has finite height $|N| \cdot h$. The ascending chain $\bot \sqsubseteq \Phi(\bot) \sqsubseteq \Phi^2(\bot) \sqsubseteq \cdots$ must stabilize within $|N| \cdot h$ steps. The limit is the least fixed point. $\square$

### 8.3 Significance

The monotone framework theorem tells us:
1. **Existence**: the analysis always has a well-defined answer.
2. **Uniqueness**: the answer is the *best* (most precise) sound approximation.
3. **Computability**: the iterative algorithm converges.
4. **Complexity**: convergence takes at most $O(|N| \cdot h)$ steps, where $h$ is the lattice height.

## 9. Beyond Bit Vectors: Non-Distributive Analyses

### 9.1 Constant Propagation

Constant propagation determines, for each variable at each point, whether it has a known constant value.

**Lattice for each variable:**

```
        top (unknown)
       / | \
      1  2  3 ...  (constant values)
       \ | /
       bottom (overdefined / not constant)
```

This is a flat lattice of height 2. The product lattice for all variables has height $2 \cdot |V|$.

**Transfer function for `x := a + b`:**

$$f(\sigma)(x) = \begin{cases} c_1 + c_2 & \text{if } \sigma(a) = c_1, \sigma(b) = c_2 \text{ (both constants)} \\ \top & \text{if } \sigma(a) = \top \text{ or } \sigma(b) = \top \\ \bot & \text{otherwise} \end{cases}$$

**Non-distributivity.** Consider two paths reaching a point where $x$ is used:
- Path 1: $a = 1, b = 2$
- Path 2: $a = 2, b = 1$

On path 1, $a + b = 3$. On path 2, $a + b = 3$. MOP gives 3 (constant).

But the MFP merges first: $a = \bot, b = \bot$ (not constant), so $a + b = \bot$.

The MFP is less precise than MOP: $\text{MOP} \sqsubset \text{MFP}$.

### 9.2 Conditional Constant Propagation

Wegman and Zadeck (1991) developed *sparse conditional constant propagation (SCCP)*, which combines constant propagation with unreachable code elimination on SSA form, achieving greater precision than the standard iterative approach.

## 10. Practical Implementation Considerations

### 10.1 Sparse Analysis on SSA Form

For many analyses, SSA form enables *sparse* computation: instead of computing dataflow values at every program point, compute them only at definition points and propagate along use-def chains. This can reduce analysis time from $O(|N|^2)$ to $O(|N| \cdot \alpha(|N|))$ or better.

### 10.2 Widening and Narrowing

For analyses over lattices of infinite height (e.g., integer intervals for range analysis), the iterative algorithm may not terminate. *Widening* ($\nabla$) forces convergence by jumping up in the lattice:

$$x \nabla y = \begin{cases} x & \text{if } y \sqsubseteq x \\ \top & \text{otherwise (or a carefully chosen overapproximation)} \end{cases}$$

*Narrowing* ($\Delta$) then refines the overapproximate result downward. Together, widening and narrowing guarantee termination while maintaining soundness, at the cost of potential precision loss.

## 11. Summary

| Concept | Key Idea |
|---------|----------|
| Lattice | Mathematical structure ensuring convergence |
| Transfer function | How each instruction transforms dataflow facts |
| Monotonicity | Guarantees fixed-point existence and computability |
| Distributivity | Ensures MFP = MOP (optimal precision) |
| Worklist algorithm | Efficient iterative fixed-point computation |
| Bit-vector frameworks | Efficient implementation using bitwise operations |

Dataflow analysis is the compiler's "eyes"---the mechanism by which it understands what programs do and identifies opportunities for improvement. The mathematical framework ensures that this understanding is both sound (never introduces bugs) and computable (always terminates with an answer).
