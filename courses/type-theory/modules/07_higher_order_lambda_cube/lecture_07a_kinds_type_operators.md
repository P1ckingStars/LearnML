# Lecture 07a: Kinds and Type Operators

> **Module 07 --- Higher-Order Types & the Lambda Cube (Weeks 13--14)**
> Estimated study time: 6--8 hours

## Learning Objectives

By the end of this lecture, you will be able to:

1. Explain why a "type of types" (i.e., a kind system) is necessary once type-level functions are admitted.
2. Define the kind language with the base kind $*$ and arrow kinds $K_1 \Rightarrow K_2$.
3. State and apply the kinding rules for type variables, type abstraction, and type application.
4. Distinguish proper types (kind $*$) from type operators (higher kinds) and classify standard constructors accordingly.
5. Perform type-level beta-reduction and determine when two type expressions are definitionally equal.
6. Formalize the analogy "terms : types :: types : kinds" and identify where it breaks down.
7. Relate the kind system to Haskell's kind inference and OCaml's module-level type constructors.
8. Prove basic metatheoretic properties of a kinding system, including uniqueness of kinds.

## 1. Motivation

### 1.1 The Need for Structure Among Types

In System F (Module 06) we introduced type variables $X$ and universal quantification $\forall X.\; T$. Every type variable ranged over the universe of all types, and no distinction was drawn between a "complete" type like $\text{Int}$ and a "parameterized" type constructor like $\text{List}$.

But consider:

- $\text{Int}$ classifies terms: $3 : \text{Int}$.
- $\text{List}$ does *not* classify any term by itself. We must apply it to an argument --- $\text{List}\;\text{Int}$ --- before we obtain a type that classifies terms such as $[1, 2, 3]$.

If we allow type variables to be instantiated with $\text{List}$, we can write nonsensical expressions like $\text{List}\;\text{List}$, which tries to pass a type operator to a type operator that expects a proper type. The resulting expression is not a well-formed type.

**The problem.** Without a classification mechanism for types themselves, there is no way to distinguish well-formed type expressions from ill-formed ones at the type level.

**The solution.** Introduce *kinds* --- a level of classification above types --- that play the same role for types that types play for terms.

### 1.2 Historical Context

| Year | Contribution | Significance |
|------|-------------|--------------|
| 1972 | Girard, System F | Polymorphism, but all type variables have the same status |
| 1974 | Reynolds, polymorphic lambda calculus | Independent rediscovery; same limitation |
| 1986 | Girard, System $F_\omega$ | Higher-order polymorphism with type operators and kinds |
| 1988 | Cardelli, "Typeful Programming" | Kinds as essential organizing principle |
| 1991 | Jones, qualified types in Haskell | Kind inference for type classes |
| 2012 | Yorgey et al., promotion in Haskell | Kind polymorphism ($\texttt{PolyKinds}$) |

### 1.3 The Stratification Principle

We extend the familiar stratification:

$$
\text{terms} \xrightarrow{\text{classified by}} \text{types} \xrightarrow{\text{classified by}} \text{kinds}
$$

Just as the typing judgment $\Gamma \vdash e : T$ ensures that a term $e$ is well-formed and has type $T$, the *kinding judgment* $\Delta \vdash T :: K$ ensures that a type expression $T$ is well-formed and has kind $K$.

## 2. Core Theory

### 2.1 The Kind Language

**Definition 2.1 (Kinds).** The set of kinds is generated by the grammar:

$$
K ::= * \mid K_1 \Rightarrow K_2
$$

where:

- $*$ (pronounced "star" or "type") is the kind of all *proper types* --- types that classify terms.
- $K_1 \Rightarrow K_2$ is the kind of *type operators* that take a type-level argument of kind $K_1$ and produce a result of kind $K_2$.

**Convention.** $\Rightarrow$ is right-associative: $K_1 \Rightarrow K_2 \Rightarrow K_3 = K_1 \Rightarrow (K_2 \Rightarrow K_3)$.

**Example 2.2.** Classifying familiar type constructors:

| Type expression | Kind | Explanation |
|----------------|------|-------------|
| $\text{Int}$ | $*$ | Proper type |
| $\text{Bool}$ | $*$ | Proper type |
| $\text{Int} \to \text{Bool}$ | $*$ | Proper type (function type) |
| $\text{List}$ | $* \Rightarrow *$ | Takes a type, returns a type |
| $\text{Pair}$ | $* \Rightarrow * \Rightarrow *$ | Takes two types, returns a type |
| $\text{Ref}$ | $* \Rightarrow *$ | Takes a type, returns a type |
| $\text{StateT}$ | $* \Rightarrow (* \Rightarrow *) \Rightarrow * \Rightarrow *$ | Monad transformer |

The last example illustrates that kinds can be *higher-order*: the second argument to $\text{StateT}$ is itself a type operator of kind $* \Rightarrow *$ (a monad).

### 2.2 Type Expressions with Operators

**Definition 2.3 (Type Expressions).** The syntax of type expressions is extended beyond System F:

$$
T ::= X \mid T_1 \to T_2 \mid \forall X::K.\; T \mid \lambda X::K.\; T \mid T_1\; T_2
$$

where:

- $X$ is a type variable.
- $T_1 \to T_2$ is the function type (a built-in binary type operator of kind $* \Rightarrow * \Rightarrow *$).
- $\forall X::K.\; T$ is universal quantification, where $X$ is bound with kind annotation $K$.
- $\lambda X::K.\; T$ is *type-level abstraction* --- a function from types to types.
- $T_1\; T_2$ is *type-level application*.

**Remark.** In System F, we wrote $\forall X.\; T$ without a kind annotation because there was only one kind (implicitly $*$). Now that we have multiple kinds, the annotation $X :: K$ is essential.

### 2.3 Kinding Contexts

**Definition 2.4 (Kinding Context).** A kinding context $\Delta$ is a finite sequence of bindings of the form $X :: K$, where each type variable appears at most once:

$$
\Delta ::= \emptyset \mid \Delta, X :: K
$$

We write $\Delta(X) = K$ to mean that $X :: K \in \Delta$.

### 2.4 Kinding Rules

The kinding judgment $\Delta \vdash T :: K$ is defined by the following inference rules.

**Rule K-Var (Type Variable).**

$$
\frac{X :: K \in \Delta}{\Delta \vdash X :: K}
$$

A type variable has the kind assigned to it in the context.

**Rule K-Arrow (Function Types).**

$$
\frac{\Delta \vdash T_1 :: * \qquad \Delta \vdash T_2 :: *}{\Delta \vdash T_1 \to T_2 :: *}
$$

Function types are proper types, and both the domain and codomain must be proper types.

**Rule K-All (Universal Quantification).**

$$
\frac{\Delta, X :: K_1 \vdash T :: *}{\Delta \vdash (\forall X :: K_1.\; T) :: *}
$$

A universally quantified type is a proper type (it classifies terms --- specifically, polymorphic terms). The body $T$ must be a proper type in the extended context.

**Rule K-Abs (Type-Level Abstraction).**

$$
\frac{\Delta, X :: K_1 \vdash T :: K_2}{\Delta \vdash (\lambda X :: K_1.\; T) :: K_1 \Rightarrow K_2}
$$

A type-level lambda abstracts over a type variable of kind $K_1$ and produces a type expression of kind $K_2$. The resulting type operator has arrow kind $K_1 \Rightarrow K_2$.

**Rule K-App (Type-Level Application).**

$$
\frac{\Delta \vdash T_1 :: K_1 \Rightarrow K_2 \qquad \Delta \vdash T_2 :: K_1}{\Delta \vdash T_1\; T_2 :: K_2}
$$

Applying a type operator of kind $K_1 \Rightarrow K_2$ to an argument of kind $K_1$ produces a result of kind $K_2$.

### 2.5 Worked Examples

**Example 2.5.** Kinding the identity type operator.

Let $T = \lambda X :: *.\; X$. We derive:

$$
\frac{X :: * \in (X :: *)}{\emptyset, X :: * \vdash X :: *}
$$

By K-Abs:

$$
\frac{\emptyset, X :: * \vdash X :: *}{\emptyset \vdash (\lambda X :: *.\; X) :: * \Rightarrow *}
$$

So the identity type operator has kind $* \Rightarrow *$.

**Example 2.6.** Kinding the constant type operator.

Let $T = \lambda X :: *.\; \lambda Y :: *.\; X$. We derive:

$$
\frac{
  \frac{X :: * \in (X :: *, Y :: *)}{X :: *, Y :: * \vdash X :: *}
}{
  X :: * \vdash (\lambda Y :: *.\; X) :: * \Rightarrow *
}
$$

By K-Abs again:

$$
\frac{X :: * \vdash (\lambda Y :: *.\; X) :: * \Rightarrow *}{\emptyset \vdash (\lambda X :: *.\; \lambda Y :: *.\; X) :: * \Rightarrow * \Rightarrow *}
$$

**Example 2.7.** Kinding a type-level application.

Let $F = \lambda X :: *.\; X \to X$ and we want to kind $F\;\text{Int}$. Assume $\text{Int} :: *$.

First, derive $F :: * \Rightarrow *$:

$$
\frac{
  \frac{X :: * \vdash X :: * \qquad X :: * \vdash X :: *}{X :: * \vdash X \to X :: *}
}{
  \emptyset \vdash (\lambda X :: *.\; X \to X) :: * \Rightarrow *
}
$$

Then by K-App:

$$
\frac{\emptyset \vdash F :: * \Rightarrow * \qquad \emptyset \vdash \text{Int} :: *}{\emptyset \vdash F\;\text{Int} :: *}
$$

And indeed $F\;\text{Int}$ reduces to $\text{Int} \to \text{Int}$, which is a proper type.

**Example 2.8.** A kind error.

Consider $\text{List}\;\text{List}$. We have $\text{List} :: * \Rightarrow *$. To form the application $\text{List}\;\text{List}$, rule K-App requires the argument to have kind $*$. But $\text{List} :: * \Rightarrow * \neq *$. Therefore the expression is *ill-kinded* and rejected.

**Example 2.9.** Higher-kinded type variable.

Consider $\lambda F :: (* \Rightarrow *).\; \lambda X :: *.\; F\;X$. We derive:

$$
\frac{
  \frac{
    F :: * \Rightarrow * \vdash F :: * \Rightarrow * \qquad X :: * \vdash X :: *
  }{
    F :: * \Rightarrow *, X :: * \vdash F\;X :: *
  }
}{
  F :: * \Rightarrow * \vdash (\lambda X :: *.\; F\;X) :: * \Rightarrow *
}
$$

And then:

$$
\frac{F :: * \Rightarrow * \vdash (\lambda X :: *.\; F\;X) :: * \Rightarrow *}{\emptyset \vdash (\lambda F :: (* \Rightarrow *).\; \lambda X :: *.\; F\;X) :: (* \Rightarrow *) \Rightarrow * \Rightarrow *}
$$

This type operator takes a unary type constructor and a type, and applies the constructor. Its kind is $(* \Rightarrow *) \Rightarrow * \Rightarrow *$.

### 2.6 Properties of the Kinding System

**Theorem 2.10 (Uniqueness of Kinds).** If $\Delta \vdash T :: K_1$ and $\Delta \vdash T :: K_2$, then $K_1 = K_2$.

*Proof.* By induction on the derivation of $\Delta \vdash T :: K_1$.

- **Case K-Var:** $T = X$ and $K_1 = \Delta(X)$. Since $\Delta$ assigns at most one kind to each variable, $K_2 = \Delta(X) = K_1$.

- **Case K-Arrow:** $T = T_a \to T_b$ and $K_1 = *$. The only rule that can derive a kind for $T_a \to T_b$ is K-Arrow, which always produces $*$. Hence $K_2 = *$.

- **Case K-All:** $T = \forall X :: K.\; S$ and $K_1 = *$. Similarly, K-All always produces $*$. Hence $K_2 = *$.

- **Case K-Abs:** $T = \lambda X :: K_a.\; S$ and $K_1 = K_a \Rightarrow K_b$ where $\Delta, X :: K_a \vdash S :: K_b$. Any derivation of $\Delta \vdash T :: K_2$ must use K-Abs, yielding $K_2 = K_a \Rightarrow K_b'$ where $\Delta, X :: K_a \vdash S :: K_b'$. By the induction hypothesis, $K_b = K_b'$, so $K_1 = K_2$.

- **Case K-App:** $T = T_1\; T_2$ and $K_1 = K'$ where $\Delta \vdash T_1 :: K'' \Rightarrow K'$ and $\Delta \vdash T_2 :: K''$ for some $K''$. Any derivation of $\Delta \vdash T :: K_2$ must use K-App: $\Delta \vdash T_1 :: K''' \Rightarrow K_2$ and $\Delta \vdash T_2 :: K'''$. By the induction hypothesis on $T_1$, $K'' \Rightarrow K' = K''' \Rightarrow K_2$, whence $K' = K_2$. $\square$

**Theorem 2.11 (Decidability of Kinding).** Given $\Delta$ and $T$, it is decidable whether there exists a $K$ such that $\Delta \vdash T :: K$.

*Proof sketch.* The kinding rules are syntax-directed: each syntactic form of $T$ determines exactly which rule applies. Moreover, the rules decrease the size of the type expression in the premises (modulo the addition of a binding to $\Delta$, which does not affect termination). Therefore a simple recursive algorithm on the structure of $T$ decides kinding. $\square$

**Lemma 2.12 (Weakening for Kinding).** If $\Delta \vdash T :: K$ and $X \notin \text{dom}(\Delta)$, then $\Delta, X :: K' \vdash T :: K$ for any kind $K'$.

*Proof.* Straightforward induction on the derivation. $\square$

**Lemma 2.13 (Substitution for Kinding).** If $\Delta, X :: K' \vdash T :: K$ and $\Delta \vdash S :: K'$, then $\Delta \vdash [X \mapsto S]T :: K$.

*Proof.* By induction on the derivation of $\Delta, X :: K' \vdash T :: K$, using Weakening as needed.

- **Case K-Var:** $T = Y$ for some type variable $Y$.
  - Subcase $Y = X$: then $K = K'$ and $[X \mapsto S]X = S$. We have $\Delta \vdash S :: K'$ by assumption.
  - Subcase $Y \neq X$: then $[X \mapsto S]Y = Y$ and $Y :: K \in \Delta$. By K-Var, $\Delta \vdash Y :: K$.

- **Case K-Arrow:** $T = T_1 \to T_2$ and $K = *$. By IH on $T_1$ and $T_2$: $\Delta \vdash [X \mapsto S]T_1 :: *$ and $\Delta \vdash [X \mapsto S]T_2 :: *$. By K-Arrow: $\Delta \vdash [X \mapsto S]T_1 \to [X \mapsto S]T_2 :: *$.

- **Case K-Abs:** $T = \lambda Y :: K_1.\; T_0$ and $K = K_1 \Rightarrow K_2$, where $\Delta, X :: K', Y :: K_1 \vdash T_0 :: K_2$. (Assume $Y \neq X$ and $Y \notin \text{FV}(S)$ by alpha-renaming.) By IH: $\Delta, Y :: K_1 \vdash [X \mapsto S]T_0 :: K_2$. By K-Abs: $\Delta \vdash \lambda Y :: K_1.\; [X \mapsto S]T_0 :: K_1 \Rightarrow K_2$.

- **Case K-App:** $T = T_1\; T_2$ where $\Delta, X :: K' \vdash T_1 :: K_a \Rightarrow K$ and $\Delta, X :: K' \vdash T_2 :: K_a$. By IH: $\Delta \vdash [X \mapsto S]T_1 :: K_a \Rightarrow K$ and $\Delta \vdash [X \mapsto S]T_2 :: K_a$. By K-App: $\Delta \vdash [X \mapsto S]T_1\; [X \mapsto S]T_2 :: K$.

- **Case K-All:** Similar to K-Abs. $\square$

## 3. Type-Level Computation

### 3.1 Type-Level Beta-Reduction

Just as the term $(\lambda x : T.\; e)\; v$ reduces to $[x \mapsto v]e$, the type expression $(\lambda X :: K.\; T)\; S$ reduces to $[X \mapsto S]T$:

$$
(\lambda X :: K.\; T)\; S \longrightarrow_\beta [X \mapsto S]T
$$

This is *type-level beta-reduction*. The substitution $[X \mapsto S]T$ replaces all free occurrences of $X$ in $T$ by $S$, avoiding capture.

**Example 3.1.** Let $\text{Pair} = \lambda X :: *.\; \lambda Y :: *.\; X \times Y$. Then:

$$
\text{Pair}\;\text{Int}\;\text{Bool} \longrightarrow_\beta (\lambda Y :: *.\; \text{Int} \times Y)\;\text{Bool} \longrightarrow_\beta \text{Int} \times \text{Bool}
$$

**Example 3.2.** The "apply" operator at the type level:

$$
(\lambda F :: (* \Rightarrow *).\; \lambda X :: *.\; F\;X)\;\text{List}\;\text{Int} \longrightarrow_\beta (\lambda X :: *.\; \text{List}\;X)\;\text{Int} \longrightarrow_\beta \text{List}\;\text{Int}
$$

### 3.2 Type-Level Eta-Reduction

By analogy with term-level eta-reduction:

$$
\lambda X :: K.\; T\; X \longrightarrow_\eta T \qquad \text{if } X \notin \text{FV}(T)
$$

### 3.3 Confluence and Strong Normalization

**Theorem 3.3 (Confluence).** Type-level beta-reduction is confluent: if $T \longrightarrow_\beta^* T_1$ and $T \longrightarrow_\beta^* T_2$, then there exists $T'$ such that $T_1 \longrightarrow_\beta^* T'$ and $T_2 \longrightarrow_\beta^* T'$.

*Proof.* The type-level language is a simply-typed lambda calculus (with kinds playing the role of types). Confluence follows from the Church--Rosser theorem for the simply-typed lambda calculus. $\square$

**Theorem 3.4 (Strong Normalization).** Every well-kinded type expression has a unique normal form under beta-reduction. Moreover, every reduction sequence terminates.

*Proof sketch.* Well-kinded type expressions correspond to well-typed terms of the simply-typed lambda calculus (kinds correspond to simple types). Strong normalization of the simply-typed lambda calculus (proved via logical relations or reducibility candidates) transfers directly. $\square$

**Corollary 3.5 (Decidability of Type Equivalence).** Two well-kinded type expressions $T_1$ and $T_2$ are beta-equivalent if and only if they have the same beta-normal form. Since normalization always terminates, type equivalence is decidable.

### 3.4 Type Equivalence

**Definition 3.6 (Definitional Equality).** Two type expressions $T_1$ and $T_2$ are *definitionally equal*, written $T_1 \equiv T_2$, if they have the same beta-eta normal form.

This relation is crucial for type checking: when checking whether a term of type $T_1$ can be used where type $T_2$ is expected, the type checker must determine whether $T_1 \equiv T_2$.

**Example 3.7.** Consider:

$$
T_1 = (\lambda X :: *.\; X \to X)\;\text{Int} \qquad T_2 = \text{Int} \to \text{Int}
$$

We have $T_1 \longrightarrow_\beta \text{Int} \to \text{Int} = T_2$, so $T_1 \equiv T_2$.

**Example 3.8.** Consider:

$$
T_1 = \lambda X :: *.\; \text{List}\;X \qquad T_2 = \text{List}
$$

By eta-reduction, $\lambda X :: *.\; \text{List}\;X \longrightarrow_\eta \text{List}$, so $T_1 \equiv T_2$ under beta-eta equivalence.

## 4. The Analogy and Its Limits

### 4.1 The Three-Level Hierarchy

The following table summarizes the three-level hierarchy:

| Level | Entities | Classification judgment | Computation rule |
|-------|----------|------------------------|-----------------|
| Terms | $e$, $v$, $\lambda x:T.\; e$ | $\Gamma \vdash e : T$ | $(\lambda x:T.\; e)\; v \to [x \mapsto v]e$ |
| Types | $T$, $\lambda X::K.\; T$ | $\Delta \vdash T :: K$ | $(\lambda X::K.\; T)\; S \to [X \mapsto S]T$ |
| Kinds | $*$, $K_1 \Rightarrow K_2$ | (no further level) | (no computation) |

The analogy is systematic:

- *Type variables* are to *kinds* as *term variables* are to *types*.
- *Type-level abstraction* $\lambda X::K.\; T$ is to *type-level application* $T_1\; T_2$ as *term-level abstraction* $\lambda x:T.\; e$ is to *term-level application* $e_1\; e_2$.
- *Kinding rules* mirror *typing rules* with one level of shift.

### 4.2 Where the Analogy Breaks

The analogy breaks in several ways:

1. **No further levels.** Kinds are not themselves classified by a higher level. One could introduce "sorts" (kinds of kinds), as in the Extended Calculus of Constructions, but the vanilla system stops here.

2. **No kind-level computation.** There are no kind-level lambdas or kind-level application. Kinds are entirely static and syntactic.

3. **No kind polymorphism.** In the basic system, we cannot quantify over kinds. Haskell's $\texttt{PolyKinds}$ extension relaxes this.

4. **Dependent types collapse the distinction.** In dependent type systems (Module 08), terms can appear in types, and the strict stratification dissolves. The lambda cube (Lecture 07d) makes this precise.

### 4.3 Formal Statement of the Analogy

The analogy can be made precise using the following dictionary:

| Term-level concept | Type-level analogue | Kind-level analogue |
|-------------------|-------------------|-------------------|
| Variable $x$ | Type variable $X$ | (none) |
| Abstraction $\lambda x : T.\; e$ | Type-level $\lambda X :: K.\; T$ | (none) |
| Application $e_1\; e_2$ | Type-level $T_1\; T_2$ | (none) |
| Type annotation $e : T$ | Kind annotation $T :: K$ | (none) |
| Beta-reduction $(\lambda x.\; e)\;v \to [x \mapsto v]e$ | $(\lambda X.\; T)\;S \to [X \mapsto S]T$ | (none) |
| Typing context $\Gamma = x_1 : T_1, \ldots$ | Kinding context $\Delta = X_1 :: K_1, \ldots$ | (none) |
| Typing judgment $\Gamma \vdash e : T$ | Kinding judgment $\Delta \vdash T :: K$ | (none) |
| Strong normalization of STLC | Strong normalization of type-level STLC | (trivial) |

Every row in the "kind-level" column is "(none)" because, in the basic system, kinds have no internal structure beyond the grammar $* \mid K_1 \Rightarrow K_2$. There are no kind-level lambdas, no kind-level variables, no kind-level application.

### 4.4 Extending the Hierarchy: Sorts

In Pure Type Systems (Lecture 07d), one introduces *sorts* to classify kinds:

$$
\text{terms} \xrightarrow{\text{:}} \text{types} \xrightarrow{\text{::}} \text{kinds} \xrightarrow{\text{:::}} \text{sorts}
$$

For example, in the Calculus of Constructions:

- $\text{Sort} = \{*, \Box\}$
- $* :: \Box$ (the kind $*$ has sort $\Box$)

This unifies the hierarchy into a single framework with a finite number of sorts.

## 5. Higher-Kinded Type Variables

### 5.1 Motivation

In System F, a polymorphic function like the identity can abstract over any type:

$$
\text{id} = \Lambda X.\; \lambda x : X.\; x \qquad : \quad \forall X.\; X \to X
$$

But what if we want to abstract over a *type constructor*? For instance, we might want a function that works for any "container" $F$ --- $\text{List}$, $\text{Tree}$, $\text{Option}$:

$$
\text{mapId} = \Lambda F :: (* \Rightarrow *).\; \Lambda X :: *.\; \lambda xs : F\;X.\; xs
$$

This requires the type variable $F$ to have kind $* \Rightarrow *$, not kind $*$. We call $F$ a *higher-kinded type variable*.

### 5.2 Kind-Annotated Quantification

In the extended system, universal quantification carries a kind annotation:

$$
\forall F :: (* \Rightarrow *).\; \forall X :: *.\; F\;X \to F\;X
$$

This is the type of a polymorphic function that operates uniformly over any unary type constructor applied to any base type.

### 5.3 Examples from Haskell

Haskell's type class system relies heavily on higher-kinded type variables:

```haskell
class Functor (f :: * -> *) where
  fmap :: (a -> b) -> f a -> f b

class Functor f => Applicative (f :: * -> *) where
  pure  :: a -> f a
  (<*>) :: f (a -> b) -> f a -> f b

class Applicative m => Monad (m :: * -> *) where
  (>>=) :: m a -> (a -> m b) -> m b
```

In each case, the type variable $f$ or $m$ has kind $* \to *$. Without higher kinds, we could not express these abstractions.

**Even higher kinds.** Monad transformers operate on type constructors of kind $* \to *$:

```haskell
class MonadTrans (t :: (* -> *) -> * -> *) where
  lift :: Monad m => m a -> t m a
```

Here $t$ has kind $(* \to *) \to * \to *$.

### 5.4 Encoding Type Constructors as Type-Level Functions

With type-level abstraction, standard type constructors become definable:

| Name | Definition | Kind |
|------|-----------|------|
| $\text{Id}$ | $\lambda X :: *.\; X$ | $* \Rightarrow *$ |
| $\text{Const}_A$ | $\lambda X :: *.\; A$ | $* \Rightarrow *$ |
| $\text{Pair}$ | $\lambda X :: *.\; \lambda Y :: *.\; X \times Y$ | $* \Rightarrow * \Rightarrow *$ |
| $\text{Arrow}$ | $\lambda X :: *.\; \lambda Y :: *.\; X \to Y$ | $* \Rightarrow * \Rightarrow *$ |
| $\text{Compose}$ | $\lambda F :: (* \Rightarrow *).\; \lambda G :: (* \Rightarrow *).\; \lambda X :: *.\; F\;(G\;X)$ | $(* \Rightarrow *) \Rightarrow (* \Rightarrow *) \Rightarrow * \Rightarrow *$ |

**Example 5.1.** Composing $\text{List}$ and $\text{Option}$:

$$
\text{Compose}\;\text{List}\;\text{Option}\;\text{Int} \longrightarrow_\beta^* \text{List}\;(\text{Option}\;\text{Int})
$$

## 6. Connection to Programming Languages

### 6.1 Haskell

Haskell has a built-in kind system that closely mirrors the formal theory:

- Base kind: `*` (or `Type` with modern syntax).
- Arrow kinds: `* -> *`, `(* -> *) -> * -> *`, etc.
- Kind inference: GHC infers kinds for type constructors and type variables.
- Kind polymorphism: with the `PolyKinds` extension, one can write `forall k (a :: k). Proxy a`.

The alignment is almost exact, except that Haskell distinguishes *lifted* and *unlifted* types at the kind level (via `TYPE` and representation polymorphism) and admits recursive type synonyms only through `newtype`.

### 6.2 OCaml

OCaml does not have a user-visible kind system in the core language. However, the module system provides analogous functionality:

- **Type constructors** in signatures: `type 'a t` is analogous to a type operator of kind $* \Rightarrow *$.
- **Functors** (parameterized modules) act as type-level functions: a functor $F : S_1 \to S_2$ maps a module matching signature $S_1$ to a module matching signature $S_2$, transforming types in the process.

The key difference is that OCaml's kind structure is implicit and restricted. One cannot write arbitrary type-level lambdas in OCaml; instead, one uses functors and parameterized types.

### 6.3 Scala

Scala has explicit higher-kinded types:

```scala
trait Functor[F[_]] {
  def map[A, B](fa: F[A])(f: A => B): F[B]
}
```

Here `F[_]` declares a type parameter of kind `* -> *`. Scala's kind system is richer than Haskell 98 but less flexible than GHC Haskell with extensions.

### 6.4 Rust

Rust does not have higher-kinded types. This is a well-known limitation. Generic associated types (GATs), stabilized in Rust 1.65, approximate some use cases:

```rust
trait Functor {
    type F<A>;
    fn fmap<A, B>(fa: Self::F<A>, f: fn(A) -> B) -> Self::F<B>;
}
```

But this is not full higher-kinded polymorphism.

## 7. Formal Metatheory: Kinding and Typing Combined

### 7.1 The Full Judgment Forms

In a system with kinds, types, and terms, we have four judgment forms:

1. $\Delta \vdash K\;\texttt{kind}$ --- $K$ is a well-formed kind (trivially decidable from the grammar).
2. $\Delta \vdash T :: K$ --- type $T$ has kind $K$ under kinding context $\Delta$.
3. $\Delta \vdash T_1 \equiv T_2 :: K$ --- types $T_1$ and $T_2$ are definitionally equal at kind $K$.
4. $\Delta; \Gamma \vdash e : T$ --- term $e$ has type $T$ under kinding context $\Delta$ and typing context $\Gamma$.

The typing context $\Gamma$ assigns types to term variables, while the kinding context $\Delta$ assigns kinds to type variables. They are kept separate but both are needed in the combined system.

### 7.2 Typing Rules (Selected)

**Rule T-Var.**

$$
\frac{x : T \in \Gamma \qquad \Delta \vdash T :: *}{\Delta; \Gamma \vdash x : T}
$$

**Rule T-Abs.**

$$
\frac{\Delta \vdash T_1 :: * \qquad \Delta; \Gamma, x : T_1 \vdash e : T_2}{\Delta; \Gamma \vdash (\lambda x : T_1.\; e) : T_1 \to T_2}
$$

**Rule T-App.**

$$
\frac{\Delta; \Gamma \vdash e_1 : T_1 \to T_2 \qquad \Delta; \Gamma \vdash e_2 : T_1}{\Delta; \Gamma \vdash e_1\; e_2 : T_2}
$$

**Rule T-TAbs (Type Abstraction).**

$$
\frac{\Delta, X :: K; \Gamma \vdash e : T}{\Delta; \Gamma \vdash (\Lambda X :: K.\; e) : \forall X :: K.\; T}
$$

**Rule T-TApp (Type Application).**

$$
\frac{\Delta; \Gamma \vdash e : \forall X :: K.\; T \qquad \Delta \vdash S :: K}{\Delta; \Gamma \vdash e\;[S] : [X \mapsto S]T}
$$

**Rule T-Eq (Type Equivalence).**

$$
\frac{\Delta; \Gamma \vdash e : T_1 \qquad \Delta \vdash T_1 \equiv T_2 :: *}{\Delta; \Gamma \vdash e : T_2}
$$

This rule allows substituting definitionally equal types. It is essential because type-level computation may produce different syntactic representations of the same type.

### 7.3 Type Safety

**Theorem 7.1 (Preservation).** If $\Delta; \Gamma \vdash e : T$ and $e \longrightarrow e'$, then $\Delta; \Gamma \vdash e' : T$.

*Proof sketch.* By induction on the derivation of $\Delta; \Gamma \vdash e : T$, using the Substitution Lemma for both term-level and type-level substitution. For beta-reduction at the type level (in T-TApp), we additionally need Lemma 2.13 (substitution for kinding). $\square$

**Theorem 7.2 (Progress).** If $\emptyset; \emptyset \vdash e : T$, then either $e$ is a value or there exists $e'$ such that $e \longrightarrow e'$.

*Proof sketch.* Standard: by induction on the derivation, using the canonical forms lemma extended to handle type abstractions. $\square$

## 8. Worked Derivation: A Complete Example

We now work through a complete kinding and typing derivation to illustrate how the layers interact.

**Goal.** Show that the polymorphic identity function, applied at a constructed type, is well-typed.

Let:

- $\text{id} = \Lambda X :: *.\; \lambda x : X.\; x$
- $F = \lambda Y :: *.\; Y \to Y$ (a type operator)

We want to derive: $\emptyset; \emptyset \vdash \text{id}\;[F\;\text{Int}]\;42 : \text{Int} \to \text{Int}$.

**Step 1.** Kind $F\;\text{Int}$.

$$
\frac{
  \frac{
    Y :: * \vdash Y :: * \quad Y :: * \vdash Y :: *
  }{
    Y :: * \vdash Y \to Y :: *
  }
}{
  \emptyset \vdash F :: * \Rightarrow *
}
\qquad
\emptyset \vdash \text{Int} :: *
$$

$$
\frac{\emptyset \vdash F :: * \Rightarrow * \qquad \emptyset \vdash \text{Int} :: *}{\emptyset \vdash F\;\text{Int} :: *}
$$

**Step 2.** Note that $F\;\text{Int} \equiv \text{Int} \to \text{Int}$ by beta-reduction.

**Step 3.** Type $\text{id}$.

$$
\frac{
  \frac{x : X \in (x : X)}{X :: *;\; x : X \vdash x : X}
}{
  X :: *;\; \emptyset \vdash (\lambda x : X.\; x) : X \to X
}
$$

$$
\frac{X :: *;\; \emptyset \vdash (\lambda x : X.\; x) : X \to X}{\emptyset;\; \emptyset \vdash (\Lambda X :: *.\; \lambda x : X.\; x) : \forall X :: *.\; X \to X}
$$

**Step 4.** Apply T-TApp with $S = F\;\text{Int}$.

$$
\frac{
  \emptyset;\; \emptyset \vdash \text{id} : \forall X :: *.\; X \to X
  \qquad
  \emptyset \vdash F\;\text{Int} :: *
}{
  \emptyset;\; \emptyset \vdash \text{id}\;[F\;\text{Int}] : [X \mapsto F\;\text{Int}](X \to X)
}
$$

Now $[X \mapsto F\;\text{Int}](X \to X) = (F\;\text{Int}) \to (F\;\text{Int})$.

**Step 5.** By type equivalence, $(F\;\text{Int}) \to (F\;\text{Int}) \equiv (\text{Int} \to \text{Int}) \to (\text{Int} \to \text{Int})$.

**Step 6.** Apply T-App with $e_2 = 42 : \text{Int}$. But wait --- the type is $(\text{Int} \to \text{Int}) \to (\text{Int} \to \text{Int})$, so the argument must have type $\text{Int} \to \text{Int}$, not $\text{Int}$. Let us correct: we should apply $\text{id}\;[F\;\text{Int}]$ to a value of type $\text{Int} \to \text{Int}$, say $\lambda n : \text{Int}.\; n + 1$.

$$
\frac{
  \emptyset;\; \emptyset \vdash \text{id}\;[F\;\text{Int}] : (\text{Int} \to \text{Int}) \to (\text{Int} \to \text{Int})
  \qquad
  \emptyset;\; \emptyset \vdash (\lambda n : \text{Int}.\; n + 1) : \text{Int} \to \text{Int}
}{
  \emptyset;\; \emptyset \vdash \text{id}\;[F\;\text{Int}]\;(\lambda n : \text{Int}.\; n + 1) : \text{Int} \to \text{Int}
}
$$

This illustrates how type-level computation (reducing $F\;\text{Int}$) interacts with term-level typing.

## 9. Kind Polymorphism (Advanced)

### 9.1 The Limitation

In the system presented so far, we cannot write a single type operator that works at multiple kinds. For example, we might want:

$$
\text{Id}_* = \lambda X :: *.\; X \qquad \text{Id}_{* \Rightarrow *} = \lambda F :: (* \Rightarrow *).\; F
$$

These are two separate definitions. A *kind-polymorphic* identity would be:

$$
\text{Id} = \lambda (k : \text{Kind}).\; \lambda X :: k.\; X \qquad :: \quad \forall k.\; k \Rightarrow k
$$

### 9.2 Universe Polymorphism

This requires *universe polymorphism* or *sort polymorphism*. In Agda:

```agda
id : {l : Level} -> {A : Set l} -> A -> A
id x = x
```

In GHC Haskell with `PolyKinds`:

```haskell
type Id :: forall k. k -> k
type family Id x where
  Id x = x
```

Kind polymorphism is closely related to the notion of *universes* in dependent type theory (Module 08).

## 10. Defunctionalization and Higher Kinds

### 10.1 The Problem Without Higher Kinds

Languages without higher-kinded types (e.g., Rust, Go, early versions of Java) face a fundamental expressiveness limitation: they cannot abstract over type constructors. Consider trying to define a generic "map" operation:

- $\text{mapList} : \forall A.\; \forall B.\; (A \to B) \to \text{List}\;A \to \text{List}\;B$
- $\text{mapOption} : \forall A.\; \forall B.\; (A \to B) \to \text{Option}\;A \to \text{Option}\;B$
- $\text{mapTree} : \forall A.\; \forall B.\; (A \to B) \to \text{Tree}\;A \to \text{Tree}\;B$

These functions share an identical structure, but without higher-kinded type variables, there is no way to write a single type that captures the pattern:

$$
\text{map} : \forall F :: (* \Rightarrow *).\; \forall A :: *.\; \forall B :: *.\; (A \to B) \to F\;A \to F\;B
$$

### 10.2 Defunctionalization as a Workaround

*Defunctionalization* (Reynolds, 1972) replaces higher-order functions with first-order data. The same idea applies at the type level. Instead of abstracting over type constructors, one introduces an explicit representation:

**Step 1.** Define a "tag" type that enumerates known constructors:

$$
\text{data TyConTag} = \text{ListTag} \mid \text{OptionTag} \mid \text{TreeTag}
$$

**Step 2.** Define an "apply" type family that interprets tags:

$$
\text{Apply}(\text{ListTag}, A) = \text{List}\;A
$$

$$
\text{Apply}(\text{OptionTag}, A) = \text{Option}\;A
$$

$$
\text{Apply}(\text{TreeTag}, A) = \text{Tree}\;A
$$

**Step 3.** Parameterize over tags instead of constructors:

$$
\text{map} : \forall (tag : \text{TyConTag}).\; \forall A.\; \forall B.\; (A \to B) \to \text{Apply}(tag, A) \to \text{Apply}(tag, B)
$$

This is verbose, non-extensible (adding a new constructor requires modifying the tag type and the apply family), and loses the parametricity guarantee. Higher-kinded types avoid all of these problems.

### 10.3 Lightweight Higher-Kinded Types

Yallop and White (2014) proposed a technique called *lightweight higher-kinded polymorphism* for languages without native support. The idea uses a "brand" type and a witness to associate the brand with a specific constructor:

In OCaml (which lacks higher-kinded type variables in the core language):

```ocaml
type ('a, 'f) app  (* abstract application type *)

(* Witnesses for specific constructors *)
type list_brand
val inj_list  : 'a list -> ('a, list_brand) app
val proj_list : ('a, list_brand) app -> 'a list
```

This encoding works but is cumbersome. It demonstrates that higher-kinded types, while simulable, provide a significantly better user experience when supported natively.

## 11. Kind Inference

### 11.1 The Inference Problem

In many systems, kind annotations can be partially or fully inferred. Given a type expression like:

$$
\lambda X.\; X \to X
$$

without an explicit kind annotation on $X$, we can infer that $X :: *$ because:
1. $X$ appears on both sides of $\to$.
2. The rule K-Arrow requires both sides to have kind $*$.
3. Therefore $X :: *$.

### 11.2 Kind Inference Algorithm

Kind inference for the kind system presented here proceeds by *constraint generation* and *unification*, analogous to Hindley--Milner type inference:

1. Assign a fresh kind variable $\kappa_X$ to each type variable $X$ that lacks a kind annotation.
2. Traverse the type expression, generating kind constraints:
   - At $T_1 \to T_2$: generate $K(T_1) = *$ and $K(T_2) = *$.
   - At $T_1\;T_2$: generate $K(T_1) = K(T_2) \Rightarrow \kappa$ for a fresh kind variable $\kappa$.
   - At $\forall X.\; T$: generate $K(T) = *$.
3. Solve the constraints by first-order unification.
4. If unification succeeds, the solution assigns concrete kinds to all kind variables. If it fails, the type expression is ill-kinded.

**Example.** Infer the kind of $\lambda F.\; \lambda X.\; F\;(F\;X)$:

- Assign $F :: \kappa_F$ and $X :: \kappa_X$.
- From $F\;X$: $\kappa_F = \kappa_X \Rightarrow \kappa_1$.
- From $F\;(F\;X)$: $\kappa_F = \kappa_1 \Rightarrow \kappa_2$.
- From the two constraints on $\kappa_F$: $\kappa_X \Rightarrow \kappa_1 = \kappa_1 \Rightarrow \kappa_2$, so $\kappa_X = \kappa_1$ and $\kappa_1 = \kappa_2$.
- Let $\kappa_X = \kappa_1 = \kappa_2 = \alpha$. Then $\kappa_F = \alpha \Rightarrow \alpha$.
- If we default $\alpha = *$, we get $F :: * \Rightarrow *$ and $X :: *$.
- Result: $\lambda F :: (* \Rightarrow *).\; \lambda X :: *.\; F\;(F\;X) :: (* \Rightarrow *) \Rightarrow * \Rightarrow *$.

GHC performs kind inference using essentially this algorithm, defaulting unconstrained kind variables to $*$ (or using `PolyKinds` to preserve the polymorphism).

**Theorem 11.3 (Principal Kinds).** For the kind language $K ::= * \mid K_1 \Rightarrow K_2$, kind inference is decidable and produces principal kinds. The principal kind of a type expression $T$ is the most general kind $K$ such that, for any other kind $K'$ derivable for $T$, $K'$ is a substitution instance of $K$.

*Proof sketch.* The kind inference problem reduces to unification in the free algebra of $*$ and $\Rightarrow$, which is unitary (has most general unifiers) by Robinson's unification theorem. $\square$

### 11.3 Defaulting and Ambiguity

When kind variables remain unconstrained, the system must decide how to default them:

- **Haskell 98/2010:** Default all unconstrained kind variables to $*$.
- **GHC with PolyKinds:** Preserve kind polymorphism by generalizing unconstrained variables.
- **OCaml:** No visible kind system; kind structure is implicit in the module system.

Defaulting to $*$ can cause surprising behavior. For example, in Haskell without `PolyKinds`, the declaration `data Proxy a = Proxy` assigns $a :: *$, preventing `Proxy` from being applied to type constructors like `Maybe`. With `PolyKinds`, the kind is inferred as $\forall k.\; k \to *$, which is more general.

## 13. Common Pitfalls and Misconceptions

### 13.1 "Every Type Has Kind $*$"

**Wrong.** In System F (without kinds), every type variable implicitly has kind $*$, and this is a reasonable mental model. But once type operators are introduced, type expressions can have non-$*$ kinds. The type expression $\text{List}$ has kind $* \Rightarrow *$, not $*$. Only when fully applied --- $\text{List}\;\text{Int}$ --- does the result have kind $*$.

### 13.2 "Types and Type Operators Are the Same Thing"

**Partially wrong.** Type operators and proper types live in the same syntactic category (type expressions), but they are distinguished by their kinds. A type operator of kind $K_1 \Rightarrow K_2$ cannot appear where a proper type of kind $*$ is expected (e.g., as the domain of a function type). The kind system enforces this distinction.

### 13.3 "Kind Checking Is Just Type Checking One Level Up"

**Mostly right, but with caveats.** The kinding rules do mirror typing rules, and the kind system is essentially a copy of the simply-typed lambda calculus. However:

- There is no kind-level lambda or kind-level application (in the basic system). Kinds are purely structural.
- There is no kind polymorphism (without extensions).
- The "types as terms" analogy works well for lambda and application but breaks down for $\forall$, which has no direct analogue in the kind system.

### 13.4 "Type-Level Reduction Can Loop"

**Wrong (for well-kinded expressions).** Strong normalization guarantees that every well-kinded type expression has a finite reduction sequence to a unique normal form. Infinite loops at the type level would make type checking undecidable. This is why the kind system is restricted to $*$ and $\Rightarrow$ (corresponding to simple types), rather than allowing recursive kinds or kind-level fixpoints.

### 13.5 "Higher-Kinded Types Require Runtime Overhead"

**Wrong.** Higher-kinded types are entirely static. Type-level computation happens during type checking and is completely erased before code generation. There is zero runtime overhead. The only cost is increased compile time for kind checking and type-level normalization.

## 14. Connecting to the Rest of the Course

### 14.1 Backward: From System F to Kinds

In System F (Module 06), we had $\forall X.\; T$ where $X$ ranged over all types. There was no distinction between $\text{Int}$ and $\text{List}$ as potential instantiations of $X$. The kind system introduced in this lecture adds the missing stratification: $X :: *$ ranges over proper types, $F :: * \Rightarrow *$ ranges over type constructors, and so on. System F is recovered as the special case where all type variables have kind $*$.

### 14.2 Forward: System $F_\omega$ and Beyond

Lecture 07b integrates type operators with polymorphism to form System $F_\omega$. The kind system of this lecture provides the foundation: the kinding rules ensure that type operators are well-formed, and the strong normalization result ensures that type equivalence (needed for type checking in $F_\omega$) is decidable.

### 14.3 Forward: Dependent Types

In the lambda cube (Lecture 07d), dependent types generalize the kind system in a radical way: types can depend on *terms*, not just on other types. The kind $\text{Nat} \to *$ (the kind of a type family indexed by natural numbers, like $\text{Vec}\;\text{Bool}$) requires the dependent-types axis. The PTS framework (also Lecture 07d) unifies types, kinds, and sorts into a single hierarchy, making the current three-level stratification a special case.

## Summary

- **Kinds** classify types the way types classify terms. The base kind $*$ classifies proper types; arrow kinds $K_1 \Rightarrow K_2$ classify type operators.
- **Type operators** are functions at the type level, written $\lambda X :: K.\; T$. They are applied via type-level application $T_1\; T_2$.
- **Kinding rules** are syntax-directed and ensure that only well-formed type expressions are admitted. The rules mirror typing rules with one level of shift.
- **Type-level computation** proceeds via beta-reduction: $(\lambda X :: K.\; T)\; S \longrightarrow_\beta [X \mapsto S]T$. This reduction is strongly normalizing and confluent for well-kinded expressions.
- **Type equivalence** is decidable: normalize both sides and compare.
- **Higher-kinded type variables** enable abstraction over type constructors, which is essential for expressing concepts like Functor, Monad, and monad transformers.
- The kind system motivates the move to System $F_\omega$ (Lecture 07b), which integrates type operators with polymorphism in a single coherent system.
